# 用项目带着学：ResolveDesk 上手路线

## 学习约定

每轮只解决一个实际问题，按“操作 → 观察证据 → 读最少代码 → 亲手改动 → 验证 → 用自己的话复述”推进。没有出现的技术不预先补齐，不以背完所有文档作为投递条件。

70 分的含义是一个可检查的门槛：能独立启动与配置、能演示一条完整业务闭环、能画请求链路、能解释三项真实取舍、能复现并定位一个失败、简历每句话都有证据。它不是“代码生成完了就能声称自己独立掌握”。

语言与框架不需要一次学全，但遇到 async/await、JSON、HTTP 状态码、SQL 事务等实际代码时，要能够读懂它们承担的工作。

## 当前真实状态（2026-10-29）

- 本地工程已实现完整售后闭环，33 个工程测试通过；浏览器完成过无密钥演示模式的工单处理与知识发布。
- SiliconFlow 的 BAAI/bge-m3 已实际返回 1024 维向量；指定 DeepSeek 部署已通过结构化输出调用。
- 三条真实模型冒烟：导入问题成功约 22.8 秒；权限问题成功约 24.8 秒；导出问题一次在协同答复阶段遇到上游请求超时，返回 502，运行状态保存为 failed。
- 失败记录的事件包含分诊完成与调查报告完成，未包含协同完成事件。结合当前 35 秒 HTTP 超时，排查应优先看协同节点的模型调用，不能先怀疑 BM25 或数据库，更不能据一次失败断言供应商总是不可用。
- 真实 Embedding 的 24 条自建检索回归已完成，数据在 reports/retrieval-live.json；不等于真实用户问答准确率。
- 当前本地 .env 选择 live，数据使用 data/resolvedesk-live.db。原 data/resolvedesk.db 与 demo 压测结果保留。配置密钥只放本地 .env，不作为学习反馈发送。

## 六轮学习顺序

| 轮次 | 先做什么 | 只补什么理论 | 亲手验证 | 面试可讲的结果 |
|---|---|---|---|---|
| 1 | 跑通导入问题，读一次运行记录 | 应用/模型/工具/知识的分工 | 找到任务事实与文档证据 | 一次请求究竟经过哪里 |
| 2 | 对比两个版本的 E2013 | RAG、BM25、向量、元数据过滤、RRF | 先比较三策略，再在测试库移除版本过滤 | 相关文档为什么也可能是错答案 |
| 3 | 读真实失败 Trace，再复现可控超时 | HTTP 超时、整体超时、异常传播、状态保存 | mock 上游变慢；确认 failed、无写入、名额释放 | 怎么定位失败在哪个节点 |
| 4 | 完成建单、技术处理与客户确认 | 工具协议、权限、幂等、事务、乐观锁 | 同一调查重复提交；旧 revision 更新 | 为什么不让模型直接操作数据库 |
| 5 | 带工单继续调查，发布并撤回案例 | Run、Session、Context、Memory 的边界 | 对比带/不带 ticket_id；重开工单撤知识 | 当前实现与长期记忆有什么区别 |
| 6 | 亲自复现一组 demo 压测，录一次演示 | 吞吐、P95/P99、429、质量评测限制 | 正确报告条件与失败比例 | 有边界、有证据的项目介绍 |

完成前四轮并能独立解释与操作，可开始整理简历和投递；后续根据真实面试问题补充，不自动增加 Redis、图谱、MCP、长程记忆或上下文压缩。

## 第一轮：用一个问题认识整套系统

### 动作一：打开系统

访问 http://127.0.0.1:8123。真实模式下若要求访问凭证，用本地样例客户凭证 `demo-customer-a`，它是本项目的本地角色凭证，和模型供应商密钥是两回事。不要把 SiliconFlow 或阿里云密钥填进网页的访问凭证。

如果服务未运行，在项目目录执行：

```powershell
uv run uvicorn app.main:app --host 127.0.0.1 --port 8123
```

先看“运行记录”里已经成功的 IMP-1001，避免为了阅读结果反复收费调用。需要亲自操作时，再在服务接待输入：

> IMP-1001 提示 E2013，升级后导入失败，请根据实际任务和适用版本说明如何处理。

### 动作二：从界面找两种证据

1. 任务事实：任务 failed、错误码 E2013、template=v1.0、accepted_rows=0。这来自当前客户任务表的工具查询。
2. 产品依据：v2.0 模板把 order_no 更名为 external_order_id。这来自知识检索。

只有文档，不能确认客户实际用了哪个模板；只有任务错误，不能可靠推断正确处理步骤。应用把两者组合，再让模型组织答复。任务数据是虚构夹具，查询与权限控制是真代码。

### 动作三：只读四个入口

- app/main.py 的 ask：接收请求、确定客户环境、可选带入工单历史。
- app/agents.py 的 run：准入、运行状态、调用整个 graph、保存成功或失败、释放名额。
- app/agents.py 的 investigate：初始证据获取、模型 Tool Call、结果回填、调用预算。
- app/agents.py 的 coordinate：结构化答复、引用校验、升级草稿。

第一轮先不通读前端、BM25 数学实现或 LangGraph 内部。能把上面四个入口串起来就够。

### 动作四：用自己的话回答

- 模型是从哪里知道客户版本的？为什么不能相信客户或模型自己填的版本？
- 任务里的 accepted_rows=0 来自哪里？检索知识库能否查出这个事实？
- 界面出现“升级草稿”，是否意味着数据库里已经有工单？真正写入发生在什么时候？

反馈模板只需要：操作是否成功、引用文档标题、一个任务事实、三问的简短回答。不要发送 .env、认证 Header 或模型密钥。

## 当前概念与代码的对应

| 概念 | 当前项目中是什么 | 不应混淆的点 |
|---|---|---|
| Run | 一次 /api/ask 调查及其状态、结果 | 一个 run 不等于一个完整会话 |
| Context | 本次请求的环境、问题、历史、召回证据、工具消息 | 是本次交给模型的信息，不是一套数据库 |
| Session | 当前没有通用 chat session 对象 | 工单可以作为业务连续性的载体，但不是完整会话系统 |
| Memory | 已解决案例与历史工单可复用 | 是业务知识/记录的复用，没有实现个人长期记忆抽取与管理 |
| RAG | 查询时检索适用文档，放进模型上下文 | 不等于模型记住文档，也不是微调 |
| Plan | 分诊路由 + 有预算的工具选择 | 没有任意长程自动任务规划 |
| Trace | 节点、工具输入输出、耗时、结果 | 不是模型隐藏思维链 |
| Usage | 当前没有持久化精确 token 与费用 | duration_ms 不能叫 token usage，后续若高频被问再实现 |

## 第三轮的现成失败案例

reports/live-smoke.json 中的导出问题返回了 502。别把修复等同于“加大超时”：先辨认是连接、读取、单节点还是总体预算，再考虑请求内容是否过长、是否存在重复工具查询、是否需要减少角色调用。

先在本地 MockTransport 中复现可控超时，确保错误可追踪、不会重复建单、并发名额释放。真实请求只进行有目的的少量复核，不用收费压测代替定位。
